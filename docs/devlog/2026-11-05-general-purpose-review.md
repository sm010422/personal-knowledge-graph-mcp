# 2026-11-05 — 범용 도구로서 점검: 엔진은 범용, 스키마는 한 사람 전용

같은 날 [조회 비용·일정·정리 도구](2026-11-05-context-cost-events-and-maintenance-tools.md)를 배포한 뒤, "다른 사람이 자기 용도로 쓸 수 있는가"를 따로 점검했다. 외부 리뷰는 코드를 보지 않고 **툴 정의와 실제 데이터만** 보고 판단했다. 그래서 리뷰의 각 지적을 코드와 대조한 뒤에 무엇을 할지 정했다.

## 1. 리뷰 요약

> 엔진은 범용, 스키마와 설명은 아직 한 사람 전용이다.

- 범용인 부분: 시점이 있는 관계(`validFrom`/`validTo`), 값 변경 이력, `user`/`inferred` 출처 구분, 명시적 도구로만 기록하는 방식
- 걸리는 부분: 엔티티·관계 타입이 개발자 커리어용이다. 공부·독서·연구·생활 기록은 전부 `RELATED_TO`로 들어간다.

## 2. 지적별 대조

| # | 리뷰 지적 | 코드 대조 결과 | 조치 |
|---|---|---|---|
| 1 | 스키마가 커리어용으로 굳어 있다 | 맞다. 타입 6개, 관계 13개 모두 커리어용 | **범용 타입 4개·관계 7개 추가** ([ADR-0012](../adr/0012-general-purpose-types.md)) |
| 2 | 툴 설명에 소유자의 색이 묻어 있다 | 맞다. `upsert_entity`의 이름 예시에 **실제 회사 이름**이 있었다. 지원 상태, 자기소개서 예시가 여러 곳에 있었다. "나 = 특정 사람"으로 묶는 것은 서버 코드에는 없고 개인 훅 프롬프트에만 있다 | **예시 범용화, 실제 이름 제거.** 본인은 `Person {isSelf: true}`로 정한다고 instructions에 명시 |
| 3 | 조회가 커지면 버티지 못한다 | 같은 날 해결: 노트 미리보기, `get_note`, `note_limit` | 기간 필터("지난주 이후 바뀐 것")와 페이지네이션은 남음 |
| 4 | 정리 도구가 없다 | 같은 날 해결: `merge_entities`, `delete_note`, `graph_stats`, `not_updated_for_days` | inferred 일괄 확인 흐름은 남음 |
| 5 | 설치가 어렵다 | 절반. `scripts/quickstart.sh`로 docker 한 번이면 뜬다. 내보내기·가져오기는 `pkg-mcp-backup export/restore`(JSONL) | SQLite 백엔드는 [ADR-0002](../adr/0002-neo4j.md)를 뒤집는 일이라 보류. Markdown 내보내기는 남음 |
| 6 | 프라이버시 | 일부 있음. 주민번호·카드번호 같은 패턴은 저장 시 거절(`policy.py`), 엔티티 단위 hard delete | 엔티티별 민감도 표시는 남음 |

리뷰가 코드를 못 봤기 때문에 3·4·5는 이미 해결된 것을 문제로 짚었다. 반대로 1·2는 코드를 보지 않아도 툴 정의만으로 보이는 문제였다. **모델과 다른 사용자가 실제로 보는 것은 코드가 아니라 툴 정의**라는 뜻이다.

## 3. 결정: 스키마 확장 방식

| 방식 | 내용 | 비용 |
|---|---|---|
| **A. 범용 타입 추가 (채택)** | `Concept`, `Resource`, `Place`, `Goal`과 관계 7개. 닫힌 어휘 유지 | 반나절 |
| B. 스키마 팩 | 타입·관계를 설정 파일로, 도메인별 프리셋 | 2~3일. enum이 툴 스키마·검증·테스트·문서 전체에 박혀 있음 |

A를 고른 이유는 [ADR-0012](../adr/0012-general-purpose-types.md)에 적었다. 요약하면 닫힌 어휘의 장점을 지키면서 바로 쓸 수 있고, B는 실제 수요가 확인된 뒤에 해도 늦지 않다.

이제 리뷰의 예시가 그대로 표현된다.

```
(고유값 분해:Concept) -PREREQUISITE_OF-> (대각화:Concept)
(선형대수 교재:Resource) -COVERS-> (고유값 분해:Concept)
(나:Person) -READ {status: reading}-> (선형대수 교재:Resource)
(나:Person) -PURSUES-> (학기말 시험 A:Goal) <-SUPPORTS- (선형대수 교재:Resource)
```

## 4. 바꾼 것

- `schema.py`: `EntityType` 4개, `RelationType` 7개 추가, `KNOWS`를 Person → Technology / Concept로 확장. 모든 관계에 규칙이 있는지 확인하는 단위 테스트와 새 관계 규칙 테스트를 추가했다.
- `server.py`: instructions와 툴 description의 예시를 범용화했다. 실제 회사 이름을 지우고, 커리어 예시 옆에 공부·독서 예시를 넣었다. "본인은 `isSelf=true`인 Person", "구체적인 타입을 고르고 `RELATED_TO`는 최후 수단"도 추가했다.
- 단위 테스트의 정규화 예시에 있던 실제 회사 이름도 가상 이름으로 바꿨다.
- 문서: `docs/schema.md`, ADR-0004 갱신 절, ADR-0012, ADR 목록.

## 5. 남은 것

- [ ] 기간 필터(`changed_since`)와 페이지네이션
- [ ] Markdown 내보내기 (사람이 읽는 백업, 다른 도구로 이전)
- [ ] inferred 확인 흐름 (inferred만 모아 보고 확정·삭제)
- [ ] 관계가 20개로 늘어난 뒤 `RELATED_TO` 비율 관찰 (첫 점검 때 6/132)
- [ ] 수요가 생기면 스키마 팩(B) 검토

## 6. 배운 점

- **툴 description은 공개 API이자 프롬프트다.** 예시 하나가 모델의 기록 경향을 정한다. 거기에 실제 이름을 쓰면 공개 레포에 개인정보를 남기는 일이기도 하다.
- **리뷰는 대조한 뒤에 반영한다.** 같은 리뷰 안에 맞는 지적(1·2)과 이미 해결된 지적(3·4·5)이 섞여 있었다. 그대로 받았다면 있는 기능을 다시 만들 뻔했다.
