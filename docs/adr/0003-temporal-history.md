# ADR-0003: 이력 — 관계는 validFrom/validTo, 속성은 Revision 노드

- 상태: Accepted
- 날짜: 2026-10-19

## 맥락

사실은 바뀐다. 지원 상태는 서류 → 면접 → 합격으로 가고, 프로젝트는 진행 중 → 일시 중지가 된다. 덮어쓰면 "언제 무엇이었나"를 잃는다. 반대로 모든 변경을 별도 노드로 버전 관리하면, 일상적인 조회(`get_context`)가 복잡해진다.

## 선택지

1. **덮어쓰기**: 단순하지만 이력이 사라진다.
2. **완전한 bitemporal 모델**: 모든 노드·관계에 유효시간과 기록시간을 둔다. 정확하지만 개인 그래프에는 과하고, 모든 쿼리에 시점 조건이 붙는다.
3. **혼합**: 의미가 큰 변화가 일어나는 **관계**는 유효기간으로 버전을 관리한다. **노드 속성**은 현재 값만 두고 변경분을 `Revision`에 남긴다.

## 결정

3번을 택한다.

- 관계: 같은 (from, type, to)에 현재 유효한 관계는 1개다. 속성이 바뀌면 기존 관계를 `validTo`로 닫고 새 관계를 만든다(`superseded`). 끝나기만 한 경우는 `end_relation`을 쓴다.
- 속성: `upsert_entity`가 바뀐 키의 before/after를 `(:Revision)-[:REVISION_OF]->(entity)`로 남긴다. `null`을 주면 속성 삭제도 이력에 남는다.

## 결과

- 기본 조회는 `validTo IS NULL` 조건 하나로 현재 상태만 본다.
- `include_history=true`면 끝난 관계와 속성 이력을 함께 보여준다. Phase 4의 "시간축 질의"는 이 구조 위에 올린다.
- 기록 시각(`createdAt`)과 유효 시작(`validFrom`)을 분리했다. "9월 1일에 지원했다"는 사실을 10월에 기록해도 날짜가 맞다.
