# ADR-0010: DB 연결은 시작을 막지 않고 백그라운드에서 재시도

- 상태: Accepted
- 날짜: 2026-10-19

## 맥락

첫 클러스터 배포에서 MCP 서버 파드가 **4번 재시작(CrashLoopBackOff)** 했고, 정상화까지 약 2분 30초가 걸렸다.

원인은 이렇다.
- 서버는 lifespan 시작 단계에서 `verify_connectivity()`를 호출하고, 실패하면 프로세스가 종료됐다.
- Neo4j는 headless Service(`clusterIP: None`)로 노출된다. headless Service의 DNS 이름은 Neo4j 파드가 Ready가 되기 전까지 아예 해석되지 않는다(`Failed to DNS resolve address neo4j:7687`).
- 재시작이 반복될수록 kubelet의 backoff가 10초, 20초, 40초…로 늘어난다. 그래서 Neo4j가 뜬 뒤에도 한참 기다렸다.

같은 클러스터에서 이미 같은 종류의 문제를 겪은 적이 있다. 추석 정전 복구 때 threat-intel-ai-service의 Kafka consumer가 브로커보다 먼저 떠서 재시도 없이 죽었다.

## 선택지

1. **initContainer로 Neo4j 대기**: 파드 정의는 단순해진다. 하지만 시작할 때만 보호되고, stdio 모드(로컬)에서는 효과가 없다.
2. **실패 시 종료 유지 + 재시작에 맡김**: 코드는 바뀌지 않지만, 위의 지연이 그대로 남는다.
3. **백그라운드 재시도 + readiness 게이트**: 프로세스는 바로 뜨고 `/health`도 응답한다. 연결과 스키마 부트스트랩은 백그라운드 태스크가 지수 백오프(2, 4, 8, 15, 15…초)로 재시도한다.

## 결정

3번이다.

- 연결 전에는 `/ready`가 503을 반환한다. 그래서 Kubernetes가 트래픽을 보내지 않는다.
- 연결 전에 툴이 호출되면 최대 10초 기다린다. 그래도 안 되면 "DB에 아직 연결되지 않음"이라는 명확한 에러를 반환한다.
- 연결 후의 일시적 끊김은 Neo4j 드라이버의 커넥션 풀이 재연결한다.

## 결과

클러스터에서 실측했다.

| 시나리오 | 이전 | 이후 |
|---|---|---|
| Neo4j와 MCP 파드 동시 재시작 | 재시작 4회, 약 150초 | **재시작 0회, 약 39초** (Neo4j Ready 17초 + 백오프 대기) |
| Neo4j만 재시작 | — | MCP 파드 영향 없음, 재시작 0회 |

- 남은 개선점: 최대 백오프 15초 때문에 Neo4j가 Ready가 된 뒤에도 최대 15초를 더 기다린다. 더 줄이려면 상한을 5초로 낮추면 된다. 대신 DB가 오래 죽어 있을 때 로그가 늘어난다.
- `logger.info` 수준의 "Connected" 로그는 현재 기본 로깅 설정에서 보이지 않는다. Phase 3에서 구조화 로깅을 붙일 때 정리한다.
